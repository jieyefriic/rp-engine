## 1. 设计研究

调研了多个 skill/harness 架构参考：
- **Anthropic Skills** — Claude Code 的 .md 文件渐进加载模型
- **Claude Code** — CLAUDE.md harness + tool-based skill loading
- **Hermes agent** — 三级渐进式上下文注入（metadata → full → references）
- **Harness engineering** — 业界共识：LLM 驱动的记忆写回需更多实践

### 关键架构决策

| 决策 | 选择 | 原因 |
|------|------|------|
| Skill 存储 | 图节点（`skill_set`） | IDE 可见、可拖拽、可组合；不是隐式 workflow 级数据 |
| 加载机制 | Tool calling（`load_skill`） | rp-engine 作为 library 在容器中运行，无本地文件系统；tool calling 已有完整链路 |
| 引用方式 | Generate 显式 `skill_sets` 字段 | 明确数据流，避免隐式继承 |
| 命名冲突 | 构建时检查 | 用户 tools 不能叫 load_skill/load_skill_reference |
| Memory writeback | 推迟 | LLM 驱动的记忆更新，业界共识尚未成熟 |
| 规则触发 | 推迟 | LLM 自触发已足够，trigger_keywords 增加复杂度 |

### 核心实现要点

1. **SkillDef** — 统一 content 和 content_file 两种来源，执行时 resolve
2. **SkillSetExecutor** — 简单：解析 config → resolve content_file → 写 state
3. **Skill index building** — generate 节点从 state 读取所有 skill_sets 引用的节点输出，合并成统一 skill 索引
4. **Metadata injection** — 构建 `## Available Skills\n- name: description\n...` 注入 system_prompt 中间层
5. **dispatch_tool_call 提取** — 从 tool calling loop 中提取 tool dispatch 逻辑，区分 built-in tool（load_skill/load_skill_reference）和 user tool（子图执行）
6. **load_skill** — 在 skill index 中查找 name，返回 content 作为 tool result
7. **load_skill_reference** — 验证 (skill_name, path) 组合合法，读取文件返回

## 5. Harness Writeback 实现

**Commit:** `5d86490`

### 改动概要

实现 harness memory 完整生命周期：读取（已有）→ 写回（新增）。Workflow 执行完成后，若配置了 `harness.writeback`，引擎发起一次专用 LLM 调用审查执行结果并更新 memory_file。

### WritebackConfig Schema

```rust
pub struct WritebackConfig {
    pub provider: String,                  // LLM provider for writeback
    pub model: String,                     // Model (can be cheap/fast)
    pub prompt: Option<String>,            // Custom prompt (sensible default if omitted)
    pub memory_char_limit: Option<usize>,  // Max chars, default 2200
}
```

### YAML 格式

```yaml
harness:
  instructions: |
    You are a helpful assistant. Always be concise.
  memory_file: "harness_memory.txt"
  writeback:
    provider: deepseek
    model: deepseek-chat
    memory_char_limit: 2200
```

### 行为要点

- Writeback 在 workflow 成功执行后触发
- **Best-effort**: writeback 失败不影响 workflow 结果（仅 warning 日志）
- 当前 run 使用 frozen snapshot，writeback 更新在下次 run 生效
- Memory 截断到 `memory_char_limit`（默认 2200 字符，~800 tokens，遵循 Hermes Agent 惯例）
- Writeback LLM 输入 = 当前 memory 内容 + workflow 最终输出
- 默认 prompt 聚焦于：用户偏好、习惯、关键决策、重要上下文

### 验证记录

```
cargo test test_harness_writeback
  → ✅ PASSED
  → memory 文件已更新，包含执行结果摘要
  → char limit 截断生效（2200 字符上限）
  → 跨 run 持久化确认：第二次 run 读取到第一次 writeback 的内容
```

### 设计哲学

Harness 承担两个角色：
- **约束**（instructions）— "你必须/不能做 X"
- **学习**（writeback）— 跨 run 积累用户偏好和模式

其他一切（skills, tools, context）都是关于扩展能力（"你可以做 X"）。Harness 是唯一的限制层和记忆层。
